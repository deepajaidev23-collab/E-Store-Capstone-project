# Phase 6 — Supabase Integration Design

## Top-Level Overview

This document designs the complete Supabase backend for BookWorm. Nothing is
implemented here. Every decision is grounded in the existing TypeScript domain
types (`book.ts`, `cart.ts`, `order.ts`, `user.ts`, `review.ts`) and the
`BookRepository` interface that the UI already depends on.

The goal is a backend where:
- Swapping `MockBookRepository` → `SupabaseBookRepository` requires changing
  **one line** in `src/repositories/index.ts`.
- The UI, hooks, and components require **zero changes**.
- Public catalogue data is readable without authentication.
- All user-owned data is protected by Row Level Security.

---

## 1. Supabase Client Configuration

### Existing client (`src/lib/supabase.ts`)

The client is already created and used by `AuthContext`. It reads two
environment variables:

```
VITE_SUPABASE_URL
VITE_SUPABASE_ANON_KEY
```

### What needs to be added

The existing `createClient` call needs a **typed database generic** once the
schema is finalised. Supabase CLI generates a `Database` type from the live
schema; the client is then typed as `createClient<Database>()`.

This unlocks:
- Auto-complete on `.from('books').select()`
- Compile-time column name checking
- Correctly typed `.data` responses — eliminating manual casts throughout
  `SupabaseBookRepository`

The `supabase.ts` file will grow by one import and one type parameter:

```ts
import type { Database } from '@/types/database.generated'
export const supabase = createClient<Database>(supabaseUrl, supabaseAnonKey)
```

No other files need to change for this.

### Service-role client

A service-role client (bypasses RLS) is only needed server-side in Edge
Functions. It must **never** be imported into the frontend bundle — the key
would be exposed to browsers. It lives only inside
`supabase/functions/_shared/supabaseAdmin.ts`.

## 3. PostgreSQL Schema — Table-by-Table Design

All tables live in the `public` schema. Primary keys are `uuid` generated by
`gen_random_uuid()`. Timestamps default to `now()`.

### Decision: which entities to include

The following entities are required because pages that already have routes
in `router.tsx` will need them:

| Entity | Required by |
|---|---|
| `profiles` | `AuthContext` trigger, `ProfilePage`, `reviews.reviewer_name` |
| `categories` | `CataloguePage` sidebar, `BookDetailPage` breadcrumb |
| `publishers` | `CataloguePage` filter, `BookDetailPage` meta |
| `books` | Every page that shows a book |
| `book_categories` | Category filter in catalogue, related-books query |
| `reviews` | `BookDetailPage` reviews section |
| `wishlists` + `wishlist_items` | `WishlistPage` (route exists, auth-guarded) |
| `carts` + `cart_items` | `CartPage`, `CheckoutPage` (routes exist, auth-guarded) |
| `addresses` | `CheckoutPage` address form |
| `coupons` | `CheckoutPage` coupon input |
| `orders` + `order_items` | `OrdersPage`, `OrderDetailPage`, `OrderConfirmationPage` |
| `payments` | `PaymentPage`, `OrderConfirmationPage` |

The following entity from the original list is **not included**:
- `book_categories` is included as a join table (covered above)

No entity is omitted that has a corresponding route or TypeScript type.

### Table: `profiles`

**Purpose:** Extends `auth.users` with application-level user data.
Supabase Auth owns authentication; this table owns display data and
reward points. It is the single source of truth for `reviewer_name` in
reviews — a join replaces the mock's `reviewer_name` field on the Review type
when using Supabase.

```sql
create table public.profiles (
  id            uuid primary key references auth.users(id) on delete cascade,
  display_name  text        not null default '',
  avatar_url    text,
  reward_points integer     not null default 0,
  created_at    timestamptz not null default now()
);
```

**Relationships:**
- `id` → `auth.users.id` (1-to-1, cascade delete)

**Indexes:**
- PK on `id` (auto)

**Notes:**
- Populated automatically on sign-up by a database trigger
  (see §8 Triggers).
- The `reviewer_name` in the mock `Review` type becomes a join from
  `profiles.display_name` in the Supabase implementation.

**Indexes:**

### Table: `books`

**Purpose:** The core catalogue entity. All catalogue queries, book detail
fetches, and order snapshots originate here.

The `author_name` and `author_bio` fields are intentionally denormalised
(no separate `authors` table). The existing domain types and all UI
components expect these directly on `Book`. A separate authors table
would require joins everywhere without adding value for the current scope.

```sql
create type public.book_format as enum ('paperback', 'ebook', 'hardcover');

create table public.books (
  id               uuid          primary key default gen_random_uuid(),
  title            text          not null,
  author_name      text          not null,
  author_bio       text,
  author_avatar_url text,
  publisher_id     uuid          references public.publishers(id) on delete set null,
  description      text          not null default '',
  cover_url        text          not null default '',
  format           book_format   not null,
  language         text          not null default 'en',
  price            numeric(10,2) not null,
  original_price   numeric(10,2),
  copies_sold      integer       not null default 0,
  average_rating   numeric(3,2)  not null default 0.00,
  is_bestseller    boolean       not null default false,
  is_new_launch    boolean       not null default false,
  created_at       timestamptz   not null default now()
);
```

**Relationships:**
- `publisher_id` → `publishers.id`
- `book_categories` join table links to `categories`

**Indexes:**
```sql
-- Full-text search across title and author_name (powers getBooks search filter)
create index books_fts_idx on public.books
  using gin(to_tsvector('english', title || ' ' || author_name));

-- Category filter (used heavily in catalogue and related-books queries)
-- Lives on book_categories, not books — see below.

-- Bestseller + new-launch flags (curated sections on home page)
create index books_bestseller_idx on public.books(is_bestseller)
  where is_bestseller = true;

create index books_new_launch_idx on public.books(is_new_launch)
  where is_new_launch = true;

-- Sort by price (price_asc / price_desc filter)
create index books_price_idx on public.books(price);

-- Sort by rating
create index books_rating_idx on public.books(average_rating desc);

-- Sort by newest
create index books_created_at_idx on public.books(created_at desc);

-- Language filter
create index books_language_idx on public.books(language);

-- Format filter
create index books_format_idx on public.books(format);

-- Publisher filter
create index books_publisher_idx on public.books(publisher_id);
```

**Notes on `average_rating`:**
Stored as a denormalised column updated by a trigger on `reviews` insert/
update/delete. Avoids an expensive aggregate on every book list query.

### Table: `book_categories`

**Purpose:** Many-to-many join between books and categories. Enables
category-based filtering in the catalogue and the related-books query.

```sql
create table public.book_categories (
  book_id     uuid not null references public.books(id)      on delete cascade,
  category_id uuid not null references public.categories(id) on delete cascade,
  primary key (book_id, category_id)
);
```

**Relationships:**
- `book_id` → `books.id`
- `category_id` → `categories.id`

**Indexes:**
```sql
-- Forward lookup: "all categories for a book" (detail page, breadcrumb)
-- Covered by the PK.

-- Reverse lookup: "all books in a category" (sidebar filter, related books)
create index book_categories_category_idx on public.book_categories(category_id);
```

### Table: `reviews`

**Purpose:** User-submitted book reviews. Displays on the book detail page.
Limited to one review per user per book by a unique constraint.

```sql
create table public.reviews (
  id         uuid        primary key default gen_random_uuid(),
  book_id    uuid        not null references public.books(id) on delete cascade,
  user_id    uuid        not null references auth.users(id)   on delete cascade,
  rating     smallint    not null check (rating between 1 and 5),
  body       text        not null,
  created_at timestamptz not null default now(),
  constraint reviews_one_per_user unique (book_id, user_id)
);
```

**Relationships:**
- `book_id` → `books.id`
- `user_id` → `auth.users.id`
- `reviewer_name` is resolved at query time by joining `profiles.display_name`

**Indexes:**
```sql
-- Fetch all reviews for a book (ordered by created_at desc)
create index reviews_book_idx on public.reviews(book_id, created_at desc);

-- Check if current user has already reviewed a book
create index reviews_user_book_idx on public.reviews(user_id, book_id);
```

**Notes on `reviewer_name`:**
The `Review` TypeScript type has `reviewer_name: string`. In the Supabase
implementation, `SupabaseBookRepository.getReviews()` joins `profiles` and
returns `profiles.display_name` as `reviewer_name`. The type contract is
preserved; the UI is unaware of the join.

**Notes on `average_rating` update:**
A database trigger fires after every INSERT/UPDATE/DELETE on `reviews` and
recomputes `books.average_rating` for the affected `book_id`:

```sql
create or replace function public.update_book_average_rating()
returns trigger language plpgsql security definer as $$
begin
  update public.books
  set average_rating = (
    select coalesce(avg(rating), 0)
    from public.reviews
    where book_id = coalesce(new.book_id, old.book_id)
  )
  where id = coalesce(new.book_id, old.book_id);
  return null;
end;
$$;

create trigger trg_update_book_rating
after insert or update or delete on public.reviews
for each row execute function public.update_book_average_rating();
```

**Purpose:** One-to-one container per user for wishlist items. Exists as a

```sql
);
```

**Relationships:**

**Indexes:**
- Unique index on `user_id` (auto from constraint)

### Table: `addresses`

**Purpose:** User-saved delivery addresses. Multiple addresses per user;

pre-fill.

```sql
create table public.addresses (
  id           uuid    primary key default gen_random_uuid(),
  user_id      uuid    not null references auth.users(id) on delete cascade,
  first_name   text    not null,
  last_name    text    not null,
  email        text    not null,
  phone        text    not null,
  address_line text    not null,
  city         text    not null,
  state        text    not null,
  country      text    not null default 'India',

);
```

**Relationships:** `user_id` → `auth.users.id`

**Indexes:**
```sql
-- "All addresses for user" — ProfilePage address manager
create index addresses_user_idx on public.addresses(user_id);
```

**Notes on `is_default`:**
Only one address per user should have `is_default = true`. This is enforced
by a database trigger (or application logic in the Edge Function) that sets
all other addresses for the same user to `false` when a new default is saved.

**Indexes:**
- Unique index on `code` (auto from constraint)

### Table: `orders`

**Purpose:** An immutable record of a completed purchase. The
`shipping_address` field is a JSONB snapshot of the address at order time —
it deliberately does not reference the `addresses` table so that editing or
deleting a saved address does not retroactively alter order history.

```sql
create type public.order_status as enum (
  'pending', 'confirmed', 'shipped', 'delivered', 'cancelled'
);

create table public.orders (
  id                      uuid         primary key default gen_random_uuid(),
  user_id                 uuid         not null references auth.users(id) on delete restrict,
  status                  order_status not null default 'pending',
  subtotal                numeric(10,2) not null,
  tax                     numeric(10,2) not null,
  delivery_charge         numeric(10,2) not null,
  coupon_id               uuid         references public.coupons(id) on delete set null,
  discount                numeric(10,2) not null default 0,
  total                   numeric(10,2) not null,
  shipping_address        jsonb        not null,
  reward_points_redeemed  integer      not null default 0,
  created_at              timestamptz  not null default now()
);
```

**Relationships:**
- `user_id` → `auth.users.id`
- `coupon_id` → `coupons.id`

**Indexes:**
```sql
-- "My orders, newest first" — OrdersPage
create index orders_user_created_idx on public.orders(user_id, created_at desc);

-- Order status filter (admin tooling, also useful for recommendations)
create index orders_status_idx on public.orders(status);
```

**Notes on `on delete restrict` for `user_id`:**
Orders must survive even if the auth user is deleted (for billing audit
purposes). `restrict` prevents accidental user deletion that would orphan
order records. Contrast with `cascade` on user-owned transient data
(carts, wishlists).

---

### Table: `order_items`

**Purpose:** Snapshot of each book in an order. The `title`, `cover_url`,
and `price` columns are snapshots taken at order time — they do not reference
the live `books` row for those values. This ensures order history is
accurate even if a book's price or title changes later. The `book_id` FK is
kept (nullable-logically via `on delete set null`) so "Buy Again" can find
the live book.

```sql
create table public.order_items (
  id        uuid          primary key default gen_random_uuid(),
  order_id  uuid          not null references public.orders(id) on delete cascade,
  book_id   uuid          references public.books(id) on delete set null,
  title     text          not null,
  cover_url text          not null default '',
  price     numeric(10,2) not null,
  quantity  integer       not null check (quantity >= 1)
);
```

**Relationships:**
- `order_id` → `orders.id`
- `book_id` → `books.id` (nullable after book deletion; title/price kept)

**Indexes:**
```sql
-- "All items for an order" — OrderDetailPage
create index order_items_order_idx on public.order_items(order_id);
```

---

### Table: `payments`

**Purpose:** Records a payment attempt for an order. Only one payment per
order is expected (unique constraint). Written exclusively by the Edge
Function using the service role — the frontend never INSERT into this table
directly. This ensures payment status cannot be spoofed from the client.

```sql
create type public.payment_method as enum (
  'credit_card', 'debit_card', 'upi', 'wallet'
);

create type public.payment_status as enum ('pending', 'success', 'failed');

create table public.payments (
  id         uuid           primary key default gen_random_uuid(),
  order_id   uuid           not null references public.orders(id) on delete restrict,
  user_id    uuid           not null references auth.users(id)    on delete restrict,
  method     payment_method not null,
  amount     numeric(10,2)  not null,
  status     payment_status not null default 'pending',
  created_at timestamptz    not null default now(),
  constraint payments_order_unique unique (order_id)
);
```

**Relationships:**
- `order_id` → `orders.id`
- `user_id` → `auth.users.id`

**Indexes:**
- Unique index on `order_id` (auto from constraint)

```sql
-- "My payment history" — ProfilePage or audit
create index payments_user_idx on public.payments(user_id);
```

## 4. Database Relationships (Entity Map)

```
auth.users (managed by Supabase)
    │
    ├─── profiles          (1:1, id = auth.users.id)
    ├─── wishlists         (1:1 via user_id)
    │       └── wishlist_items ──→ books
    ├─── carts             (1:1 via user_id)
    │       └── cart_items     ──→ books
    ├─── addresses         (1:N via user_id)
    ├─── orders            (1:N via user_id)
    │       ├── order_items    ──→ books (snapshot)
    │       └── payments       (1:1 via order_id)
    └─── reviews           (N:M via book_id+user_id)
    
books
    ├── publishers         (N:1 via publisher_id)
    ├── book_categories    ──→ categories
    └── reviews            (1:N via book_id)

coupons
    └── orders             (1:N via coupon_id, nullable)
```

## 5. Migrations

### Strategy

All schema changes are managed as numbered SQL migration files in
`supabase/migrations/`. The Supabase CLI applies them in order with
`supabase db push` (remote) or `supabase db reset` (local dev).

### Migration files (one per logical concern)

```
supabase/migrations/
  20250001000000_create_enums.sql
  20250001000001_create_profiles.sql
  20250001000002_create_catalogue.sql        -- categories, publishers, books, book_categories
  20250001000003_create_reviews.sql
  20250001000004_create_user_data.sql        -- wishlists, carts, addresses
  20250001000005_create_commerce.sql         -- coupons, orders, order_items, payments
  20250001000006_create_indexes.sql
  20250001000007_enable_rls.sql
  20250001000008_create_rls_policies.sql
  20250001000009_create_triggers.sql         -- profile auto-create, average_rating update
  20250001000010_seed_catalogue.sql          -- categories, publishers, books (mirrors mockData.ts)
```

### Why separate files per concern

Each migration is independently reviewable, reversible (with a matching
`down` script), and git-blameable. Grouping by concern (enums → tables →
indexes → RLS → triggers → seed) ensures dependencies are always satisfied
in order.

### Local development workflow

```bash
# Start local Supabase stack
supabase start

# Apply all migrations
supabase db reset

# Generate TypeScript types after schema stabilises
supabase gen types typescript --local > src/types/database.generated.ts
```

## 6. Generated TypeScript Types

### What Supabase CLI generates

Running `supabase gen types typescript` produces a single file:

```
src/types/database.generated.ts
```

This file is **auto-generated and never hand-edited**. It contains a
`Database` type with nested `Tables`, `Views`, `Functions`, and `Enums`
namespaces. Example shape:

```ts
export type Database = {
  public: {
    Tables: {
      books: {
        Row: { id: string; title: string; price: number; /* ... */ }
        Insert: { id?: string; title: string; price: number; /* ... */ }
        Update: { id?: string; title?: string; price?: number; /* ... */ }
      }
      // ... all other tables
    }
    Enums: {
      book_format: 'paperback' | 'ebook' | 'hardcover'
      order_status: 'pending' | 'confirmed' | 'shipped' | 'delivered' | 'cancelled'
      // ...
    }
  }
}
```

### Relationship to hand-written domain types

The hand-written types (`src/types/book.ts`, `cart.ts`, `order.ts`, etc.) are
**the source of truth for the UI**. They are not replaced by the generated
types. Instead, `SupabaseBookRepository` maps generated `Row` types to the
hand-written domain types. This isolates the UI from database column renames.

Example mapping pattern inside `SupabaseBookRepository`:

```ts
// Generated type
type BookRow = Database['public']['Tables']['books']['Row']

// Mapping function — lives inside SupabaseBookRepository
function rowToBook(row: BookRow, categories: Category[], publisher?: Publisher): Book {
  return {
    id: row.id,
    title: row.title,
    author_name: row.author_name,
    // ...
    categories,
    publisher,
  }
}
```

### Gitignore decision

`database.generated.ts` should be **committed** to the repository (not
gitignored) so that CI can typecheck without running a live Supabase
instance. It is regenerated after every schema migration.

## 7. SupabaseBookRepository Implementation Design

### File location

```
src/repositories/supabase/SupabaseBookRepository.ts
```

### Class structure

```ts
export class SupabaseBookRepository implements BookRepository {
  // All 11 methods from the BookRepository interface
  getBooks(filters: BookFilters): Promise<BooksResult>
  getBookById(id: string): Promise<Book | null>
  getCategories(): Promise<Category[]>
  getPublishers(): Promise<Publisher[]>
  getRecommendedBooks(): Promise<Book[]>
  getBestsellerBooks(): Promise<Book[]>
  getNewLaunchBooks(): Promise<Book[]>
  getReviews(bookId: string): Promise<Review[]>
  submitReview(bookId: string, rating: number, body: string): Promise<Review>
  getRelatedBooks(bookId: string, categoryIds: string[]): Promise<Book[]>
}
```

### Key query designs

#### `getBooks(filters)` — Catalogue query

Uses PostgREST's composable query builder. Search uses the `@@` full-text
operator against the GIN index. All filters are applied conditionally
(same logic as `MockBookRepository` but via `.filter()` / `.textSearch()`).

Categories require a join through `book_categories`. The PostgREST
`!inner` join syntax filters to books that have the matching category.

Sort maps `SortField` → `{ column, ascending }` pairs.

The response includes embedded `publisher` (via FK), `categories` (via
`book_categories!inner(categories(*))`), so the `Book` shape is assembled
in one round trip.

#### `getReviews(bookId)` — With reviewer name

```sql
select reviews.*, profiles.display_name as reviewer_name
from reviews
join profiles on profiles.id = reviews.user_id
where reviews.book_id = $1
order by reviews.created_at desc
```

In PostgREST syntax this is expressed as a Supabase select with an embedded
join: `.select('*, profiles(display_name)')`.

#### `getRelatedBooks(bookId, categoryIds)` — Same-category books

```sql
select books.*, ...
from books
join book_categories bc on bc.book_id = books.id
where bc.category_id = any($1)
  and books.id != $2
order by books.copies_sold desc
limit 3
```

#### `submitReview(bookId, rating, body)` — Insert with upsert

Uses `.upsert()` on `(book_id, user_id)` to handle the one-review-per-user
constraint gracefully (re-submitting updates the existing review rather than
throwing a 409).

## 9. Public Catalogue Access

These tables are readable by any visitor (including unauthenticated / anon
role) because the catalogue must be browsable without sign-in.

```sql
-- categories: public read
create policy "anyone can read categories"
  on public.categories for select
  using (true);

-- publishers: public read
create policy "anyone can read publishers"
  on public.publishers for select
  using (true);

-- books: public read
create policy "anyone can read books"
  on public.books for select
  using (true);

-- book_categories: public read (required for category filter join)
create policy "anyone can read book_categories"
  on public.book_categories for select
  using (true);

-- reviews: public read (reviews are visible to all)
create policy "anyone can read reviews"
  on public.reviews for select
  using (true);

-- coupons: authenticated read only (needed to validate a coupon code at checkout)
create policy "authenticated users can read active coupons"
  on public.coupons for select
  using (auth.role() = 'authenticated' and is_active = true);
```

**No writes** are permitted from the anon role on any table. Every write
requires authentication.

## 10. User-Owned Data Access

### `profiles`

```sql
-- A user can only read their own profile
create policy "user reads own profile"
  on public.profiles for select
  using (auth.uid() = id);

-- A user can update their own profile
create policy "user updates own profile"
  on public.profiles for update
  using (auth.uid() = id)
  with check (auth.uid() = id);

-- Insert is handled by the trigger only — no direct client insert policy needed.
-- The trigger runs as security definer, so it bypasses RLS.
```

```sql
-- Authenticated users can insert reviews for any book
create policy "authenticated users can insert reviews"

create policy "users manage own reviews"

  using (auth.uid() = user_id)
```


## 11. Error Handling Design

### Supabase client error shape

Every Supabase query returns `{ data, error }`. The `SupabaseBookRepository`
must:
1. Check `if (error) throw error` after every query.
2. Return `null` (not throw) when `getBookById` finds no row
   (handled by checking `data === null` before throwing).

### React Query integration

`useQuery` and `useMutation` already handle thrown errors via their `error`
property. The UI components already render `ErrorState` and `Alert` for these
cases. No changes to the UI error handling are needed.

### Error types the repository will throw

| Scenario | Error |
|---|---|
| Network failure | Supabase `FetchError` — caught by react-query, shown via `ErrorState` |
| RLS violation | Supabase `PostgrestError` with code `42501` — should be treated as auth error |
| Unique constraint violation | Code `23505` — surfaced as "You have already reviewed this book" in `Alert` |
| Row not found (`getBookById`) | Returns `null`, page renders `NotFoundState` — not thrown |

### Edge Function error contract

The payment Edge Function returns a typed JSON response:

```ts
{ success: boolean; orderId?: string; error?: string }
```

The `PaymentPage` checks `success` and shows `PaymentErrorState` on
`success: false`, or navigates to `/order-confirmation/:orderId` on success.

## 12. Profile Auto-Create Trigger

To ensure every authenticated user has a `profiles` row without a dedicated
sign-up API call:

```sql
create or replace function public.handle_new_user()
returns trigger language plpgsql security definer set search_path = public as $$
begin
  insert into public.profiles (id, display_name)
  values (new.id, coalesce(new.raw_user_meta_data->>'display_name', split_part(new.email, '@', 1)));
  return new;
end;
$$;

create trigger on_auth_user_created
after insert on auth.users
for each row execute function public.handle_new_user();
```

This trigger runs as `security definer` so it can insert into `profiles`
even though no client-side RLS INSERT policy exists for `profiles`.

## 14. Open Questions for Review

1. **`copies_sold` maintenance** — Is `copies_sold` updated by a trigger on
   `order_items` insert, or is it a periodic batch job? A trigger is simpler
   but adds latency to the order-creation path. A nightly batch is safer.

2. **`is_bestseller` / `is_new_launch` flags** — Are these set manually by
   an admin, or computed automatically (e.g. `is_new_launch` = created within
   last 30 days)? Automatic computation could be a Postgres generated column
   or a view.

3. **`reviewer_name` in `Review` type** — The mock has this as a plain
   string field. In production it comes from a join on `profiles`. Should the
   TypeScript `Review` type keep `reviewer_name` (populated by the repo), or
   should it become a nested `profile: { display_name }` object? Keeping it
   flat preserves the existing UI with zero changes.

4. **One review per user** — The unique constraint enforces this at the DB
   level. Should the UI also prevent re-submission (disable the form if a
   review from `auth.uid()` already exists for the book)? This requires
   a query to check existence before rendering the form.

5. **Edge Function scope** — The plan assigns order creation + payment
   recording + cart clearing to a single Edge Function. Should this be one
   function (`process-payment`) or two (`create-order` + `record-payment`)?
   One function is simpler; two is more testable and allows retrying payment
   without re-creating the order.
